# Profile Analyzer UI: LLM Brief

**Version**: 1.0.0  
**Date**: December 2024  
**Purpose**: Reference guide for LLM sessions performing performance analysis using the Profile Analyzer UI  
**Companion To**: `v3_59_2__timestamp-capture__llm-usage-brief.md`

---

## Overview

The Profile Analyzer is a browser-based visualization tool for profiling data generated by the `@timestamp` decorator system. It transforms JSON profiling output into interactive charts, tables, and tree views that support performance optimization workflows.

**Key Capability**: Compare profiling runs before/after code changes to measure improvements or detect regressions.

---

## Data Sources

The analyzer accepts two types of profiling output files:

### Summary Files (`summary_*.json`)
```json
{
  "response_type": "summary",
  "traces": {
    "total_duration_ms": 61.49,
    "method_count": 31,
    "entry_count": 930,
    "hotspots": [
      { "name": "method_name", "self_ms": 15.23, "percentage": 24.8, "calls": 45 }
    ]
  }
}
```
**Use for**: Quick hotspot identification, comparison between runs, total time tracking.

### Full Trace Files (`full_*.json`)
```json
{
  "response_type": "full",
  "traces": {
    "metadata": {
      "total_duration_ms": 61.49,
      "entry_count": 930,
      "method_count": 31
    },
    "entries": [...],  // Raw enter/exit events
    "call_tree": [...]  // Hierarchical execution tree
  }
}
```
**Use for**: Per-call analysis, O(n) detection, execution flow exploration, deep algorithmic investigation.

## Analysis Modes

### Summary Mode

Access by selecting "Summary" toggle in the header. Designed for aggregate analysis.

#### Single Profile View
**Purpose**: Examine one profiling run in detail.

**Components**:
- **Metrics Cards**: Total ms, method count, entry count, HTML size (if create_stats paired)
- **Hotspots Bar Chart**: Horizontal bars showing self-time per method
- **Hotspot Table**: Sortable by self_ms, percentage, calls, ms/call

**Analysis Questions Answered**:
- Where is time being spent?
- Which methods have high self-time?
- What's the per-call cost of each method?

#### Comparison View
**Purpose**: A/B comparison between profiling runs.

**Requirements**: Select 2+ profiles using checkboxes.

**Components**:
- **Baseline Selector**: Dropdown to choose reference profile
- **Grouped Bar Chart**: Methods side-by-side across profiles
- **Delta Tables**: Shows +/- ms and % change per method
- **Color Coding**: Green = improvement (faster), Red = regression (slower)

**Analysis Questions Answered**:
- Did my change make things faster or slower?
- Which methods improved? Which regressed?
- What's the total time delta?

#### Scaling View
**Purpose**: Analyze how performance scales with input size.

**Requirements**: Select 2+ profiles with numeric size data.

**Components**:
- **Total Duration Chart**: Line plot of total_ms vs input size
- **Top Methods Scaling**: Multi-line chart of self_ms per method vs size

**Analysis Questions Answered**:
- Is total time growing linearly with input?
- Which methods contribute most to scaling cost?

---

### Full Mode

Access by selecting "Full" toggle in the header. Designed for deep per-call analysis.

#### Method Stats View
**Purpose**: Aggregated statistics derived from the call tree.

**Components**:
- **Metrics Cards**: Total ms, method count, entry count, total calls
- **Methods Bar Chart**: Total self-time per method
- **Statistics Table**: Columns for count, total self, avg self, min, max, spread (max/min ratio)
- **Call Distribution Chart**: Click a table row to see per-call timing sequence

**Analysis Questions Answered**:
- How consistent is each method's timing?
- Are there outlier calls (high spread)?
- Does timing vary through execution (early vs late calls)?

#### Per-Call Scaling View ⭐
**Purpose**: Detect O(n) algorithmic complexity within methods.

**This is the most diagnostic view for optimization work.**

**Components**:
- **Overall Chart**: Average ms per call vs entry count
- **Method Scaling Chart**: Per-method avg self-time per call vs entry count
- **Method Scaling Table**: Checkboxes to show/hide methods, trend indicators
- **Overall Scaling Table**: Profile-by-profile breakdown

**Key Insight**: 
- **Flat line** = O(1) per call — the method does constant work regardless of input size ✓
- **Rising line** = O(n) per call — the method does MORE work as input grows ⚠️

**Analysis Questions Answered**:
- Which methods have O(n) per-call behavior?
- After a fix, did the line flatten?
- Is there hidden quadratic behavior (O(n) method called O(n) times)?

**Interactive Features**:
- Click any line to hide it (useful for removing dominant methods that obscure others)
- Hover to highlight line and see detailed tooltip
- Hover syncs with table row highlighting
- Maximize button for full-screen analysis

#### Call Tree View
**Purpose**: Explore the actual execution hierarchy.

**Components**:
- **Expandable Tree**: Click ▶ to expand, ▼ to collapse
- **Node Information**: Method name, total duration, self-time, % of total
- **Visual Emphasis**: Background tint proportional to self-time percentage
- **Controls**: Collapse All / Expand All buttons

**Analysis Questions Answered**:
- What's the actual call sequence?
- Where in the tree is time concentrated?
- What called the slow method?

## Workflow: Before/After Comparison

The primary use case for performance optimization work:

### Step 1: Capture Baseline
```python
_timestamp_collector_ = Timestamp_Collector(name="baseline")
with _timestamp_collector_:
    result = my_function(test_data)
# Export full trace
```

### Step 2: Make Code Changes
Implement optimization, refactor, fix algorithmic issue.

### Step 3: Capture After
```python
_timestamp_collector_ = Timestamp_Collector(name="after_fix")
with _timestamp_collector_:
    result = my_function(test_data)
# Export full trace
```

### Step 4: Compare in Profile Analyzer

**For quick comparison** (Summary Mode → Comparison View):
- Load both summary files
- Select both profiles
- Set baseline to "before"
- Review delta table for improvements/regressions

**For algorithmic verification** (Full Mode → Per-Call Scaling):
- Load both full trace files
- Select both profiles
- Check if previously-rising lines are now flat
- Verify no new rising lines appeared

## Interpreting Results

### Healthy Patterns

| Observation | Interpretation |
|-------------|----------------|
| Flat lines in Per-Call Scaling | O(1) per-call complexity ✓ |
| Green cells in Comparison delta | Performance improved ✓ |
| Low spread in Method Stats | Consistent timing ✓ |
| Self-time concentrated in leaf methods | Expected — work happens at leaves |

### Warning Patterns

| Observation | Interpretation |
|-------------|----------------|
| Rising line in Per-Call Scaling | O(n) per-call — investigate ⚠️ |
| Red cells in Comparison delta | Performance regressed ⚠️ |
| High spread (10x+) in Method Stats | Inconsistent timing — cache? GC? ⚠️ |
| High self-time in orchestrator methods | Unexpected — should be near zero ⚠️ |

### Critical Patterns

| Observation | Interpretation |
|-------------|----------------|
| Steeply rising line that was flat | New O(n) bug introduced 🔴 |
| Total time growing faster than linear | Possible O(n²) lurking 🔴 |
| Method appears in hotspots post-fix | Fix moved problem, didn't solve it 🔴 |

|--------|---------|
| Method | Fully qualified method name |

| Column | Meaning |
|--------|---------|

| Calls | Total invocation count |
| Total Self | Sum of self_ms across all calls |

| Min | Fastest call |
| Max | Slowest call |

### Scaling Table Columns
| Column | Meaning |
|--------|---------|

## Tips for Analysis Sessions

1. **Start with Per-Call Scaling** when investigating algorithmic complexity
2. **Hide the root pipeline method** first — it always dominates and obscures others
3. **Use maximize** for dense charts with many methods
4. **Check spread** for methods with high variance
5. **Cross-reference** hotspots with call tree to understand context
6. **Save screenshots** of before/after scaling charts as evidence

## Appendix A: Data Source Schema Reference

This appendix provides complete schema documentation for the two JSON file formats supported by the Profile Analyzer. These files are generated by the `@timestamp` decorator instrumentation system.

---

### A.1 Summary File Schema

**Filename pattern**: `summary_*.json`  
**Generated by**: `Timestamp_Collector.to_summary()` or analysis endpoints  
**Purpose**: Aggregated performance overview with hotspot identification

#### Complete Structure

```json
{
  "response_type": "summary",
  "graph": null,
  "traces": {
    "total_duration_ns": 61491334,
    "total_duration_ms": 61.491334,
    "method_count": 31,
    "entry_count": 930,
    "start_time_ns": 10262061660585291,
    "end_time_ns": 10262061722076625,
    "hotspots": [
      {
        "name": "Html_MGraph__Body.process_element",
        "self_ms": 15.2341,
        "percentage": 24.78,
        "calls": 287
      }
    ]
  }
}
```

#### Field Definitions

| Field | Type | Description |
|-------|------|-------------|
| `response_type` | string | Always `"summary"` for this format |
| `graph` | null \| object | Optional graph data (usually null in summary) |
| `traces` | object | Container for all timing data |

#### `traces` Object

| Field | Type | Description |
|-------|------|-------------|
| `total_duration_ns` | integer | Total execution time in nanoseconds |
| `total_duration_ms` | float | Total execution time in milliseconds |
| `method_count` | integer | Number of unique methods instrumented |
| `entry_count` | integer | Total number of method enter/exit pairs recorded |
| `start_time_ns` | integer | Absolute timestamp when profiling started (nanoseconds since epoch) |
| `end_time_ns` | integer | Absolute timestamp when profiling ended |
| `hotspots` | array | List of methods sorted by self-time (descending) |

#### `hotspots[]` Array Elements

| Field | Type | Description |
|-------|------|-------------|
| `name` | string | Fully qualified method name (e.g., `ClassName.method_name`) |
| `self_ms` | float | Time spent in this method excluding time in child calls |
| `percentage` | float | `self_ms` as percentage of `total_duration_ms` |
| `calls` | integer | Number of times this method was invoked |

#### Key Concept: Self-Time vs Total-Time

**Self-time** (`self_ms`) is the actual CPU time spent executing code within a method, excluding any time spent in methods it calls. This is the critical metric for identifying optimization targets.

Example:
```
process() calls parse() and transform()

process():     total=100ms, self=5ms   ← orchestration overhead only
  parse():     total=30ms,  self=30ms  ← leaf method, self=total
  transform(): total=65ms,  self=40ms  ← some work, some in children
    helper():  total=25ms,  self=25ms  ← leaf method
```

The hotspot list would show: `transform` (40ms), `parse` (30ms), `helper` (25ms), `process` (5ms)

### A.2 Full Trace File Schema

**Filename pattern**: `full_*.json`  
**Generated by**: `Timestamp_Collector.to_full()` or analysis endpoints  
**Purpose**: Complete execution trace with call tree for deep analysis

#### Complete Structure

```json
{
  "response_type": "full",
  "graph": null,
  "traces": {
    "metadata": {
      "name": "profiling_session_name",
      "total_duration_ns": 61491334,
      "total_duration_ms": 61.491334,
      "entry_count": 930,
      "method_count": 31,
      "start_time_ns": 10262061660585291,
      "end_time_ns": 10262061722076625
    },
    "entries": [
      {
        "event_type": "enter",
        "name": "Pipeline.execute",
        "timestamp_ns": 10262061660585291,
        "call_index": 0,
        "depth": 0
      },
      {
        "event_type": "exit",
        "name": "Pipeline.execute",
        "timestamp_ns": 10262061722076625,
        "call_index": 0,
        "depth": 0,
        "duration_ns": 61491334,
        "duration_ms": 61.491334
      }
    ],
    "call_tree": [
      {
        "name": "Pipeline.execute",
        "call_index": 0,
        "depth": 0,
        "duration_ns": 61491334,
        "duration_ms": 61.491334,
        "self_ns": 2145000,
        "self_ms": 2.145,
        "children": [
          {
            "name": "Parser.parse_html",
            "call_index": 1,
            "depth": 1,
            "duration_ns": 15234000,
            "duration_ms": 15.234,
            "self_ns": 15234000,
            "self_ms": 15.234,
            "children": []
          }
        ]
      }
    ]
  }
}
```

#### Top-Level Fields

| Field | Type | Description |
|-------|------|-------------|
| `response_type` | string | Always `"full"` for this format |
| `graph` | null \| object | Optional graph data (usually null) |
| `traces` | object | Container for metadata, raw entries, and call tree |

#### `traces.metadata` Object

| Field | Type | Description |
|-------|------|-------------|
| `name` | string | Name given to the `Timestamp_Collector` instance |
| `total_duration_ns` | integer | Total execution time in nanoseconds |
| `total_duration_ms` | float | Total execution time in milliseconds |
| `entry_count` | integer | Total enter/exit event pairs |
| `method_count` | integer | Count of unique methods |
| `start_time_ns` | integer | Profiling start timestamp |
| `end_time_ns` | integer | Profiling end timestamp |

#### `traces.entries[]` Array (Raw Events)

The entries array contains the raw enter/exit events in chronological order.

**Enter Event:**
| Field | Type | Description |
|-------|------|-------------|
| `event_type` | string | `"enter"` |
| `name` | string | Method name being entered |
| `timestamp_ns` | integer | Absolute timestamp of entry |
| `call_index` | integer | Sequential call number (0-based) |
| `depth` | integer | Call stack depth (0 = root) |

**Exit Event:**
| Field | Type | Description |
|-------|------|-------------|
| `event_type` | string | `"exit"` |
| `name` | string | Method name being exited |
| `timestamp_ns` | integer | Absolute timestamp of exit |
| `call_index` | integer | Matches the enter event's call_index |
| `depth` | integer | Call stack depth |
| `duration_ns` | integer | Time from enter to exit (nanoseconds) |
| `duration_ms` | float | Time from enter to exit (milliseconds) |

#### `traces.call_tree[]` Array (Hierarchical Structure)

The call tree represents the execution as a hierarchy, with parent methods containing their children.

**Tree Node:**
| Field | Type | Description |
|-------|------|-------------|
| `name` | string | Method name |
| `call_index` | integer | Sequential call number |
| `depth` | integer | Nesting level (0 = root entry point) |
| `duration_ns` | integer | Total time including children (nanoseconds) |
| `duration_ms` | float | Total time including children (milliseconds) |
| `self_ns` | integer | Time excluding children (nanoseconds) |
| `self_ms` | float | Time excluding children (milliseconds) |
| `children` | array | Nested array of child call nodes |

#### Understanding the Call Tree

The call tree mirrors the actual execution stack. Consider this code:

```python
@timestamp
def process(self, data):
    parsed = self.parse(data)      # Call 1
    result = self.transform(parsed) # Call 2
    return result

@timestamp
def parse(self, data):
    return self.tokenize(data)     # Call 3

@timestamp  
def tokenize(self, data):
    # leaf method
    return tokens

@timestamp
def transform(self, data):
    # leaf method
    return output
```

Execution sequence: `process` → `parse` → `tokenize` → (return) → (return) → `transform` → (return) → (return)

Resulting call tree:
```json
{
  "name": "process",
  "call_index": 0,
  "depth": 0,
  "duration_ms": 100.0,
  "self_ms": 2.0,
  "children": [
    {
      "name": "parse",
      "call_index": 1,
      "depth": 1,
      "duration_ms": 45.0,
      "self_ms": 5.0,
      "children": [
        {
          "name": "tokenize",
          "call_index": 2,
          "depth": 2,
          "duration_ms": 40.0,
          "self_ms": 40.0,
          "children": []
        }
      ]
    },
    {
      "name": "transform",
      "call_index": 3,
      "depth": 1,
      "duration_ms": 53.0,
      "self_ms": 53.0,
      "children": []
    }
  ]
}
```

**Invariant**: For any node, `self_ms = duration_ms - sum(children[].duration_ms)`

### A.4 Filename Conventions and Key Extraction

The analyzer extracts a "key" from each filename to group related files:

**Extraction Rules:**
1. Remove file extension (`.json`)
2. Remove prefix (`summary_`, `full_`, `create_stats_`, `speedscope_`)
3. Strip leading/trailing underscores

**Examples:**

| Filename | Extracted Key |
|----------|---------------|
| `summary_____with_size__30.json` | `with_size__30` |
| `full_____with_size__30.json` | `with_size__30` |
| `create_stats_____with_size__30.json` | `with_size__30` |
| `full_____simple-html.json` | `simple-html` |
| `full_____html-for-url__https___www_gov_uk__json` | `html-for-url__https___www_gov_uk__json` |

Files with matching keys are grouped as a single "profile" in the UI, allowing summary and create_stats data to be displayed together.

### A.5 Entry Count as Scaling Metric

The `entry_count` field represents the number of instrumented method calls recorded during profiling. This serves as a proxy for "workload size" and is used as the X-axis in scaling analysis.

**Why entry_count?**
- Present in all profiling files (no filename parsing required)
- Directly proportional to actual work performed
- Comparable across different test inputs
- Range typically: 100s (small) to 50,000+ (large)

**Scaling Analysis Logic:**
- Profiles are sorted by `entry_count` (ascending)
- X-axis shows entry count values
- Y-axis shows timing metrics (total ms, avg ms/call)
- Flat lines indicate O(1) behavior
- Rising lines indicate O(n) or worse

### A.7 Generating Test Data: QA_Create_Html_Transformations

The profiling data files are generated using the `QA_Create_Html_Transformations` utility class. This tool orchestrates the HTML-to-MGraph conversion pipeline with full instrumentation enabled.

**Location**: `mgraph_ai_service_html_graph.utils.testing.QA_Create_Html_Transformations`

#### Basic Usage

```python
from mgraph_ai_service_html_graph.utils.testing.QA_Create_Html_Transformations import QA_Create_Html_Transformations
from osbot_utils.utils.Files import path_combine

# Configure output folder
target_folder = path_combine(__file__, '../_traces')
create_html_transformations = QA_Create_Html_Transformations(target_folder=target_folder)

# Generate traces using context manager
with create_html_transformations as _:
    _.create__for__simple_html()
    _.create__for__html_with_some_tags()
    _.create__for__html_bootstrap_example()
```

#### Available Generation Methods

| Method | Description | Output Key |
|--------|-------------|------------|
| `create__for__simple_html()` | Minimal HTML structure | `simple-html` |
| `create__for__html_with_some_tags()` | HTML with various tag types | `html-with-some-tags` |
| `create__for__html_bootstrap_example()` | Bootstrap-based HTML | `html-bootstrap-example` |
| `create__for__html__with_size(n)` | Generated HTML with n elements | `with_size__N` |
| `create__for__url(url)` | Fetch and process live URL | `html-for-url__URL` |
